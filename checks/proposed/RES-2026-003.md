id: RES-2026-003
title: Access packages grant privileged access that Entra's privileged-role block does not cover
source: https://securitylabs.datadoghq.com/articles/entra-access-packages-part-1-privileges/   published: 2026-11-19   author: Katie Knowles, Datadog Security Labs
services: Entra ID Governance — entitlement management (catalogs, access packages, assignment
  policies, catalog resources and resource roles, ID Governance delegated roles); Entra
  role-assignable groups; Azure RBAC assignments held by groups that packages hand out
summary: Entitlement management bundles access — group membership or ownership, application
  roles, SharePoint and Teams access — into access packages that users request or are assigned,
  under a policy that decides who may ask and whether anyone approves. Entra refuses to put a
  role it flags as privileged directly into a package, and the research argues that boundary is
  narrower than it looks: roles that are not flagged still carry real power outside Entra (the
  article names Billing Administrator, Exchange Administrator, Power Platform Administrator and
  Azure DevOps Administrator), and a role-assignable group that holds Global Administrator can be
  added to a catalog as an ordinary group resource, so the package delivers the role through
  group membership instead. The delegation model is the other half: a Catalog Creator becomes
  owner of the catalogs it creates, and a Catalog Owner controls the resources, packages and
  policies of catalogs it owns, so control of a catalog is control of everything that catalog can
  hand out. Someone who gains eligibility for such a package, or control of such a catalog, gets
  what the package grants without ever being assigned a privileged Entra role. This is part one
  of a series — the product structure and role model are documented, the attack paths are stated
  as theory, and the worked examples are promised for a later post.
vendor_status: by design per vendor; tenant action required to scope catalogs and policies —
  Microsoft documents granting Entra roles through a role-assignable group in an access package
  as a supported scenario: https://learn.microsoft.com/entra/id-governance/entitlement-management-overview
  and https://learn.microsoft.com/entra/id-governance/entitlement-management-delegate
exposure_condition: an access package reaches principals more loosely than the access it carries.
  Two limbs, either of which is exposure; rate them separately.
  Limb 1 — both halves must hold for the same package:
    (A) grant: at least one of the package's resource roles resolves to privileged access —
        Member or Owner of a group whose isAssignableToRole is true; Member or Owner of a group
        that holds an Azure RBAC role at subscription or management-group scope; Owner on any
        group that gates such access; or a directory role resource that Entra does not flag as
        privileged but that carries tenant-wide power outside Entra.
    (B) reach: a policy attached to that package has allowedTargetScope of allMemberUsers,
        allDirectoryUsers, allExternalUsers, allConfiguredConnectedOrganizationUsers,
        allDirectoryServicePrincipals or allDirectoryAgentIdentities; OR
        requestApprovalSettings.isApprovalRequiredForAdd is false; OR automaticRequestSettings is
        present (auto-assignment — no request and no approval at all); OR reviewSettings.isEnabled
        is false and expiration sets no end date.
  Limb 2 — authoring reach: a principal holds Catalog Owner or Access Package Manager on a
    catalog that contains an (A) resource, or holds Catalog Creator at the entitlement management
    scope, while not already holding a privileged directory role. That principal can write the
    package and its policy, so today's policy settings do not bound it.
  (A) on its own is governed privileged access and is the point of the product. It is not
  exposure by itself, and (B) on a package that grants nothing sensitive is not either.
applicability: entitlement management requires a Microsoft Entra ID Governance or Microsoft Entra
  Suite subscription (Microsoft states some capabilities may work with Entra ID P2). An assessor
  tells from inventory two ways: GET /v1.0/subscribedSkus for an ID Governance or Entra Suite
  plan — naming varies, so treat it as corroboration, not the test — and, decisively, step 1 of
  the reader_query. If catalogs returns nothing, or only the built-in General catalog with no
  resources and no access packages anywhere, the feature is not in use: not_applicable.
reader_query: |
  All Microsoft Graph calls are v1.0 GETs. Microsoft documents Global Reader as a supported
  directory role for steps 1, 2 and 4; steps 5 and 6 are ordinary directory reads; step 8 needs
  Azure Reader. Steps 3 and 7 carry a permissions caveat, noted inline. Nothing here writes.

  # 1. Catalogs, and which packages live in each.
  GET /identityGovernance/entitlementManagement/catalogs?$expand=accessPackages
      # keep per catalog: id, displayName, catalogType, state, isExternallyVisible
      # (isExternallyVisible true means external/connected-organization users can be in scope).

  # 2. What each catalog actually governs — the grant side, (A).
  GET /identityGovernance/entitlementManagement/catalogs/{catalogId}/resources?$expand=roles,scopes
      # keep originSystem (AadGroup, AadApplication, SharePointOnline, ...), originId, displayName,
      # and each role's displayName (Member / Owner / app role).
      # For an AadGroup resource, originId is the group objectId — the join key for steps 5, 6, 8.

  # 3. Package -> resource role mapping, if permitted.
  GET /identityGovernance/entitlementManagement/accessPackages?$expand=resourceRoleScopes($expand=role,scope)
      # Microsoft lists Global Reader as supported for listing accessPackages, but the permissions
      # note on resourceRoleScopes names only Identity Governance Administrator among directory
      # roles. If this returns 403, drop to catalog granularity: steps 1 and 2 still show which
      # catalog holds the privileged resource and which packages sit in that catalog. Say in the
      # finding which granularity was used.

  # 4. Reach side, (B).
  GET /identityGovernance/entitlementManagement/assignmentPolicies?$expand=accessPackage
      # per policy keep: allowedTargetScope, specificAllowedTargets,
      # requestApprovalSettings.isApprovalRequiredForAdd and .stages, automaticRequestSettings
      # (present => auto-assignment policy), reviewSettings.isEnabled, expiration.

  # 5. Which of the catalog's groups are role-assignable.
  GET /groups?$filter=isAssignableToRole eq true&$count=true&$select=id,displayName,isAssignableToRole
      # advanced query: send header  ConsistencyLevel: eventual

  # 6. What directory roles those groups hold, and which role definitions Entra calls privileged.
  GET /roleManagement/directory/roleAssignments?$expand=principal
  GET /roleManagement/directory/roleDefinitions?$select=id,displayName,isPrivileged,isBuiltIn
      # isPrivileged null means the classification is unavailable, not that the role is harmless.

  # 7. Who holds entitlement management's own roles — limb 2.
  GET /roleManagement/entitlementManagement/roleDefinitions?$select=id,displayName
  GET /roleManagement/entitlementManagement/roleAssignments?$expand=principal
      # appScopeId is /AccessPackageCatalog/{catalogId} for catalog-scoped roles; entitlement-
      # management-wide for Catalog Creator and Connected Organization Administrator.
      # Catalog owner ae79f266-94d4-4dab-b730-feca7e132178
      # Access package manager 7f480852-ebdc-47d4-87de-0d8498384a83
      # Catalog creator ba92d953-d8e0-4e39-a797-0cbedb0a89e8
      # Needs EntitlementManagement.Read.All. Microsoft's page for this call does not enumerate
      # directory roles for the entitlement management provider, so Global Reader is expected to
      # work but is not documented for it. A 403 makes limb 2 not_assessable, not limb 1.
      # This call returns explicit assignments only — not rights held via a directory role or via
      # membership of a group that is assigned one.

  # 8. Azure RBAC held by the groups found in step 2 (Azure Reader). Azure Resource Graph:
  authorizationresources
  | where type == "microsoft.authorization/roleassignments"
  | extend principalId = tostring(properties.principalId),
           roleDefinitionId = tostring(properties.roleDefinitionId),
           scope = tostring(properties.scope)
  | where principalId in~ (<group objectIds from step 2>)
  | project subscriptionId, principalId, roleDefinitionId, scope
      # or per group: az role assignment list --assignee <groupObjectId> --all --include-inherited -o json
result_logic: exposed if any package satisfies both (A) and (B) — limb 1 — or if any principal
  matches limb 2. Report the limbs separately, and name the catalog, the package, the resource
  role and the policy setting that triggered it. not_exposed if entitlement management is in use
  and every package carrying an (A) resource is scoped to specificDirectoryUsers or to
  administrative assignment, with isApprovalRequiredForAdd true, an expiry set and reviews
  enabled, and no principal outside the privileged-role holders has Catalog Owner, Access Package
  Manager or Catalog Creator over those catalogs. not_applicable per applicability above.
  not_assessable if step 1, 2 or 4 is refused. If only step 3 is refused, rate at catalog
  granularity and state that in the finding. If only step 7 is refused, rate limb 1 and mark
  limb 2 not_assessable.
blind_spots: this check reads configuration, not state. Current assignments, pending requests,
  approval history and who approved what are not read here, so a package whose policy is tight
  today may already have handed out access. Whether an approver is a real control is invisible:
  the approver may be a group the requester can join, or the requester's own manager, and nothing
  in these objects shows whether approvals are rubber-stamped. Transitive reach is invisible —
  nested membership, dynamic membership rules and group-ownership chains can make an (A) group
  reachable by paths entirely outside entitlement management, and steps 6 and 8 only resolve
  direct assignments to the group. What a resource actually opens is invisible: SharePoint and
  Teams content sensitivity, what an app role means inside its application, and Azure RBAC at
  scopes below the one assigned. isPrivileged classifies only microsoft.directory actions and is
  nullable, so it says nothing about Exchange, Power Platform or Azure DevOps power — deciding
  which unflagged roles matter is a judgement the query cannot make. Package-level precision may
  be unavailable at Global Reader (step 3). And limb 2 exists because the policy read today is
  not a bound on what a catalog owner can create tomorrow.
false_positives: a package whose only privileged-looking resource is a role-assignable group that
  currently holds no role — isAssignableToRole true is a capability, not a grant; check step 6
  before rating. Auto-assignment policies are the normal mechanism for joiner/mover provisioning
  and only matter combined with (A). isApprovalRequiredForAdd false on a package whose
  specificAllowedTargets is already a small vetted set is weaker than it looks. Catalog Owner
  held by the same people who already hold Identity Governance Administrator or Global
  Administrator is no escalation. A group whose directory role is PIM-eligible rather than active
  still needs activation, with whatever controls PIM applies — a weaker finding than an active
  role assignment, not the same one.
related_baseline: CIS Microsoft Azure Foundations — Entra ID section (privileged role assignment
  and access review controls); MCSB PA-1, PA-7. No control in either benchmark addresses
  entitlement management catalogs or access package policies directly, so this check is not
  covered by a baseline today.
recommendation: treat any catalog holding a role-assignable group, or a group with Azure RBAC at
  subscription or management-group scope, as a privileged catalog — put those resources in their
  own catalog so that delegating ordinary catalogs cannot reach them. On that catalog's packages,
  scope policies to specific directory users or administrative assignment, require approval by
  someone outside the requester's reach, set an expiry and enable access reviews. Do not treat
  the privileged-role block as a boundary: enumerate what each catalog's groups actually hold.
  Keep Catalog Creator, Catalog Owner and Access Package Manager on privileged catalogs to the
  people who already hold Identity Governance Administrator, and review them catalog by catalog,
  since catalog-scoped assignments do not appear in a tenant-wide directory role review. Set
  catalogs that do not need external collaboration to not be externally visible.
confidence: medium — the configuration state is readable and the structural facts are documented
  by the vendor, but the research states its impact as theory in this part with examples promised
  later, and the package-to-resource expansion may be refused at Global Reader, costing precision.
