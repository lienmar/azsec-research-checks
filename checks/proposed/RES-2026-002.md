id: RES-2026-002
title: APIM Classic instances holding secrets through the November 2026 exposure window,
  with no evidence of rotation since the platform fix
source: https://techcommunity.microsoft.com/blog/integrationsonazureblog/rotating-credentials-in-azure-api-management/4575478   published: 2026-11-21 (updated 2026-11-22)   author: Microsoft (Azure Integration Services Blog)
services: Azure API Management — Classic tiers (Developer, Basic, Standard, Premium);
  named values, backends, loggers, OAuth 2.0 authorization servers, OpenID Connect providers,
  developer portal identity providers, API subscription keys, legacy management API access keys,
  certificates, policy documents. Entra ID application credentials, where an APIM OAuth/OIDC
  object is backed by an Entra app registration.
summary: A flaw in Azure API Management Classic allowed an unauthorized party to read secrets
  held in customer instances. Microsoft deployed a platform mitigation that closed the access
  path, but that mitigation does not invalidate any credential read before it landed. Anything
  stored in an affected instance during the window — named value secrets, backend keys and
  client certificates, OAuth and OIDC client secrets, Event Hubs connection strings, subscription
  keys, legacy management API keys, and secrets written literally into policy — must be treated
  as known to an attacker until rotated at the system that issued it. The residual risk is
  entirely tenant-side: a tenant that has patched nothing (there is nothing for it to patch) and
  rotated nothing is in exactly the state the attacker left it in. This check looks for Classic
  instances that existed through the window, inventories what secret-bearing objects they hold,
  and then looks for control-plane evidence that those objects were rewritten afterwards.
vendor_status: fixed platform-side on 2026-11-19; tenant action required: rotate every credential
  held in an affected instance during the window —
  https://techcommunity.microsoft.com/blog/integrationsonazureblog/rotating-credentials-in-azure-api-management/4575478
  CAVEAT ON SOURCING, read before relying on this field: the cited primary source is a
  credential-rotation how-to. It names the credential classes an APIM instance can hold and it
  states that updating a value in API Management does not revoke the old credential at its
  issuer. It does NOT describe a vulnerability, name affected or unaffected tiers, give an
  identification or mitigation date, or say that anything was exploited. Every incident fact in
  this check — exploitation in the wild, identification 2026-11-18, mitigation 2026-11-19, scope
  limited to the Classic Developer/Basic/Standard/Premium tiers with the v2 tiers unaffected —
  comes from Azure Service Health advisory MZK9-GH0 and from the Norwegian NSM advisory of
  2026-11-20 (updated 2026-11-23), neither of which was retrievable while writing this check.
  MZK9-GH0 is tenant-scoped and readable only from inside a notified tenant's Service Health
  blade. Before running this check on an engagement, pull MZK9-GH0 from the client's own Service
  Health history and confirm the dates and the tier list against it; if they differ, the date
  boundaries below are wrong and must be corrected.
exposure_condition: an API Management instance whose sku.name is one of Developer, Basic,
  Standard or Premium (the Classic tiers), which existed before the 2026-11-19 mitigation, AND
  which holds at least one secret-bearing object (a named value marked secret, a backend with
  header / query / authorization credentials or a client certificate, a logger with a connection
  string, an OAuth 2.0 authorization server, an OpenID Connect provider, a developer portal
  identity provider, an active API subscription, or enabled legacy tenant access), AND for which
  there is no control-plane evidence that the object was rewritten after the mitigation landed.
  Not-exposed requires evidence of rotation for every secret-bearing class the instance holds;
  partial rotation is still exposure for the classes left alone.
applicability: run the Step 1 Resource Graph query across every subscription in scope. If it
  returns no row whose tier is Classic, the tenant has nothing in scope and the result is
  not_applicable. v2 instances (BasicV2, StandardV2, PremiumV2) are reported by the query for
  completeness and are then excluded. Consumption is reported separately and NOT auto-excluded —
  see blind_spots; the primary source places it in neither group.
reader_query: |
  All steps below are read-only. Azure Reader plus Entra Global Reader is sufficient for every
  call. Record presence and shape only — never persist a credential value into engagement notes.

  OUT OF SCOPE, DO NOT RUN. Reading a stored secret's value needs a POST action that Reader does
  not hold and that this check deliberately excludes:
    POST .../namedValues/{id}/listValue        (a.k.a. /listSecrets)
    POST .../authorizationServers/{id}/listSecrets
    POST .../openidConnectProviders/{id}/listSecrets
    POST .../identityProviders/{type}/listSecrets
    POST .../subscriptions/{sid}/listSecrets
    POST .../tenant/access/listSecrets
    ...and every regeneratePrimaryKey / regenerateSecondaryKey action.
  The check establishes that a secret EXISTS and was not rotated. It never reads one.

  ---- Step 1. Inventory: which instances are Classic, and did they exist in the window ----
  Azure Resource Graph (portal, or `az graph query -q`), across all subscriptions in scope:

    resources
    | where type =~ 'microsoft.apimanagement/service'
    | extend skuName = tostring(sku.name)
    | extend tier = case(
        skuName in~ ('Developer','Basic','Standard','Premium'), 'Classic',
        skuName in~ ('BasicV2','StandardV2','PremiumV2'),       'v2',
        skuName =~ 'Consumption',                               'Consumption-UNRESOLVED',
        'Unknown-INVESTIGATE')
    | extend createdAtUtc = todatetime(properties.createdAtUtc)
    | extend inWindow = iff(isnull(createdAtUtc) or createdAtUtc < datetime(2026-11-19T00:00:00Z),
                            'yes-or-unknown', 'no-created-after-fix')
    | project id, name, subscriptionId, resourceGroup, location, skuName, tier,
              capacity = toint(sku.capacity),
              platformVersion = tostring(properties.platformVersion),
              createdAtUtc, inWindow,
              publicNetworkAccess = tostring(properties.publicNetworkAccess),
              identityType = tostring(identity.type),
              gatewayUrl = tostring(properties.gatewayUrl),
              tags
    | order by tier asc, name asc

  Carry forward every row where tier == 'Classic' and inWindow != 'no-created-after-fix'.
  A null createdAtUtc is treated as in-window: absence of a timestamp is not evidence of
  recent creation.

  ---- Step 2. Per instance, enumerate the secret-bearing objects (Reader GETs) ----
  For each carried-forward instance, with SVC = its full resource id and AV = 2024-05-01.
  Every call below is a GET; `az rest --method get` is used so the verb is explicit.

    # Named values. properties.value is not returned for secrets; keyVault refs are visible.
    az rest --method get --url "https://management.azure.com${SVC}/namedValues?api-version=${AV}"
    # Record per entry: name, properties.displayName, properties.secret,
    #   whether properties.keyVault exists, keyVault.secretIdentifier (and whether it is
    #   VERSIONED — a trailing /{version} segment — or unversioned/auto-refreshing),
    #   keyVault.lastStatus.code and .timeStampUtc, properties.tags.

    # Backends. WARNING: unlike named values, the backend contract documents no GET-time
    # omission for credentials, and Microsoft's own published example returns header, query
    # and authorization parameter values inline. Expect live secret material in this response.
    # Record presence and field names ONLY. Do not save the body.
    az rest --method get --url "https://management.azure.com${SVC}/backends?api-version=${AV}"
    # Record per entry: name, properties.url, and which of credentials.header,
    #   credentials.query, credentials.authorization, credentials.certificate,
    #   credentials.certificateIds, proxy.username are present.

    # Loggers — Event Hubs connection strings live here.
    az rest --method get --url "https://management.azure.com${SVC}/loggers?api-version=${AV}"
    # Record: name, loggerType, resourceId, and whether credentials.connectionString is a
    #   {{named-value}} reference or a literal.

    # OAuth 2.0 authorization servers. clientSecret is NOT returned on GET.
    # resourceOwnerPassword and tokenBodyParameters values ARE returned — treat as secret.
    az rest --method get --url "https://management.azure.com${SVC}/authorizationServers?api-version=${AV}"
    # Record: name, clientId, grantTypes, tokenEndpoint, whether resourceOwnerUsername /
    #   resourceOwnerPassword are set, tokenBodyParameters[].name.

    # OpenID Connect providers. clientSecret NOT returned on GET.
    az rest --method get --url "https://management.azure.com${SVC}/openidConnectProviders?api-version=${AV}"
    # Record: name, clientId, metadataEndpoint.

    # Developer portal sign-in identity providers. clientSecret NOT returned on GET.
    az rest --method get --url "https://management.azure.com${SVC}/identityProviders?api-version=${AV}"
    # Record: type (aad, aadB2C, google, facebook, ...), clientId, authority.

    # Certificates uploaded to the instance.
    az rest --method get --url "https://management.azure.com${SVC}/certificates?api-version=${AV}"
    # Record: name, thumbprint, expirationDate, keyVault.secretIdentifier if present.

    # API subscriptions. Keys are NOT returned on GET. There is no key-rotation timestamp.
    az rest --method get --url "https://management.azure.com${SVC}/subscriptions?api-version=${AV}"
    # Record: count, and per entry name, scope, state, createdDate.

    # Legacy management API access. Returns enabled + principalId, not the keys.
    az rest --method get --url "https://management.azure.com${SVC}/tenant/access?api-version=${AV}"
    # If properties.enabled is true, legacy management API keys exist and are a rotation target.

    # Policy documents may contain literal secrets. Optional, and it returns secret material
    # when it is there — read on screen, record only whether a literal credential appears.
    az rest --method get --url "https://management.azure.com${SVC}/policies/policy?format=rawxml&api-version=${AV}"
    # Per-API policies: enumerate .../apis?api-version=${AV} then .../apis/{apiId}/policies/policy

  An instance with zero hits across all of the above holds nothing to rotate — see result_logic.

  ---- Step 3. Rotation evidence: Azure Activity Log (the only Reader-visible signal) ----
  No APIM object carries a per-credential lastModified field, so rotation can only be inferred
  from control-plane write events. Reader's */read covers the activity-log list operation.
  Run per subscription in scope:

    az monitor activity-log list \
      --namespace Microsoft.ApiManagement \
      --start-time 2026-11-19T00:00:00Z \
      --end-time   <assessment date, ISO 8601 Z> \
      --max-items  5000 \
      --query "[].{time:eventTimestamp, resource:resourceId, op:operationName.value,
                   result:status.value, caller:caller}" \
      -o json

  Equivalent REST, if the CLI namespace filter behaves unexpectedly — filter by resourceProvider,
  NOT by the parent resourceUri: child writes carry the CHILD resource id, so a resourceUri
  filter pinned to the service would silently miss every one of them.

    GET https://management.azure.com/subscriptions/{subId}/providers/Microsoft.Insights/eventtypes/management/values
        ?api-version=2015-04-01
        &$filter=eventTimestamp ge '2026-11-19T00:00:00Z'
                 and eventTimestamp le '{assessmentDate}'
                 and resourceProvider eq 'Microsoft.ApiManagement'

  Group the returned events by instance (resourceId prefix) and classify by operationName:

    MICROSOFT.APIMANAGEMENT/SERVICE/NAMEDVALUES/WRITE                → named value rotated
    MICROSOFT.APIMANAGEMENT/SERVICE/BACKENDS/WRITE                   → backend credential rotated
    MICROSOFT.APIMANAGEMENT/SERVICE/LOGGERS/WRITE                    → logger connection string rotated
    MICROSOFT.APIMANAGEMENT/SERVICE/AUTHORIZATIONSERVERS/WRITE       → OAuth client secret rotated
    MICROSOFT.APIMANAGEMENT/SERVICE/OPENIDCONNECTPROVIDERS/WRITE     → OIDC client secret rotated
    MICROSOFT.APIMANAGEMENT/SERVICE/IDENTITYPROVIDERS/WRITE          → portal sign-in secret rotated
    MICROSOFT.APIMANAGEMENT/SERVICE/CERTIFICATES/WRITE               → certificate replaced
    MICROSOFT.APIMANAGEMENT/SERVICE/SUBSCRIPTIONS/REGENERATE*KEY/ACTION  → subscription key rotated
    MICROSOFT.APIMANAGEMENT/SERVICE/TENANT/REGENERATE*KEY/ACTION     → management API key rotated
    MICROSOFT.APIMANAGEMENT/SERVICE/POLICIES/WRITE
    MICROSOFT.APIMANAGEMENT/SERVICE/APIS/POLICIES/WRITE              → policy literal possibly changed

  Count an event as rotation evidence only when status.value is Succeeded AND eventTimestamp is
  on or after 2026-11-20T00:00:00Z. Collect from 2026-11-19T00:00:00Z but treat 19 November
  itself as a grey zone: per-region mitigation completion times are not published, so a secret
  written on the 19th may have been written while the instance was still reachable. List
  grey-zone events for the client rather than crediting them.

  ---- Step 4. Issuer-side rotation evidence for Entra-backed secrets (Global Reader) ----
  This is the one place the assessment can see rotation at the ISSUER rather than just inside
  APIM. For every clientId collected from authorizationServers, openidConnectProviders and
  identityProviders in Step 2, look it up as an Entra application appId:

    GET https://graph.microsoft.com/v1.0/applications?$select=id,appId,displayName,passwordCredentials,keyCredentials
    GET https://graph.microsoft.com/v1.0/servicePrincipals?$select=id,appId,displayName,passwordCredentials,keyCredentials

  Secret VALUES are never returned — only metadata. For each matched app, read
  passwordCredentials[].startDateTime and keyCredentials[].startDateTime. A credential whose
  startDateTime is on or after 2026-11-20T00:00:00Z was minted after the fix and is real
  issuer-side rotation evidence. An app whose only credentials all start before 2026-11-18 has
  not been rotated at the issuer, whatever the APIM object looks like. Also record any
  credential still valid (endDateTime in the future) that predates the window — that is the
  compromised secret, still live.

result_logic: |
  not_applicable  — Step 1 returns no Classic-tier instance in scope.
  not_applicable (per instance) — a Classic instance whose createdAtUtc is on or after
                    2026-11-19T00:00:00Z. It did not exist through the window.
  not_applicable (per instance) — a Classic instance that existed in the window but where Step 2
                    finds no secret-bearing object of any class: no secret named value, no backend
                    credentials, no logger connection string, no OAuth/OIDC/identity provider, no
                    subscriptions, and tenant access disabled. Nothing was there to take.
  exposed         — a Classic instance that existed through the window, holds at least one
                    secret-bearing object, and has at least one secret-bearing CLASS with no
                    qualifying rotation evidence from Step 3 (or, for Entra-backed OAuth/OIDC
                    objects, from Step 4). Report per class, not per instance: an instance that
                    rotated its named values but never regenerated a subscription key is exposed
                    on subscription keys. Partial rotation does not clear an instance.
  not_exposed     — every secret-bearing class the instance holds shows a Succeeded control-plane
                    write or regenerate event on or after 2026-11-20, and every Entra-backed
                    OAuth/OIDC clientId has a passwordCredential or keyCredential minted on or
                    after that date with no pre-window credential still valid. State plainly in
                    the finding that this is evidence of rotation inside Azure, not proof of
                    revocation at third-party issuers — that part needs client confirmation and
                    cannot be reached with these two roles.
  not_assessable  — the assessment runs after roughly 2027-02-17 (2026-11-19 plus the 90-day
                    Activity Log retention) and the client has no diagnostic export of the
                    activity log to a Log Analytics workspace or storage account; or the
                    subscription's activity log is not readable; or the Step 2 child GETs are
                    denied because Reader is scoped below the subscription. Step 1 and Step 2 can
                    still establish that Classic instances hold secrets — report that as a
                    partial finding and say that the rotation half could not be determined.
blind_spots: |
  Reader and Global Reader cannot establish the following, and no amount of querying will change
  that. These are limits of the roles, not gaps in the query.

  1. Whether a given secret was actually rotated at its ISSUER. This is the central blind spot
     and the primary source makes the same point: writing a new value into API Management does
     not revoke the old one where it is honoured. An APIM namedValues/write proves only that the
     instance now holds a different string. A third-party API key, a partner OAuth client secret
     or an on-prem system credential may still be live. Step 4 closes this for Entra-issued
     secrets only; everything else needs the client to confirm.
  2. Credential values. Deliberately so — the listValue / listSecrets POST actions are excluded
     by design. The check therefore cannot compare a current value against a known-compromised
     one, and cannot detect rotation that produced an identical string.
  3. The unauthorized access itself. The Azure Activity Log records control-plane writes, not
     reads, and Microsoft documents that requests rejected at authentication or authorization
     never generate an entry at all. Whatever path was used before 2026-11-19 is not in the
     tenant's log, and there is no Reader-visible per-tenant "were you accessed" signal. That
     determination lives in MZK9-GH0 and in whatever Microsoft notified the client directly.
     Absence of evidence here is not evidence of absence — read the advisory.
  4. Anything older than 90 days. Activity Log default retention is 90 days with no charge and no
     configuration. The rotation window for this check closes around 2027-02-17, after which the
     check degrades to not_assessable unless the tenant exported the log. Worth telling the
     client early: an export set up now preserves the record; one set up in March does not.
  5. Rotation that never touches ARM. A named value holding an UNVERSIONED Key Vault secret
     identifier auto-refreshes from the vault, so the correct remediation — rotate the secret in
     Key Vault, let APIM pick it up — generates no APIM control-plane event whatsoever. Key Vault
     secret writes are data-plane and are absent from the activity log by design. Such an
     instance reads as unrotated when it is in fact remediated. Check Key Vault-backed named
     values by hand.
  6. Key Vault secret version history. Reading secret metadata (versions, created and updated
     timestamps) is a Key Vault data-plane operation requiring the Key Vault Reader role or an
     equivalent access policy. Azure Reader does not grant it. If the client grants Key Vault
     Reader for the engagement, this blind spot closes for every Key Vault-backed named value and
     the check gets materially stronger — worth asking for.
  7. Per-credential timestamps. Confirmed against the vendor API reference: the named value,
     backend, logger, authorization server, OpenID Connect provider and identity provider
     contracts carry no lastModified field of any kind. Subscription keys are worse — the
     subscription object exposes createdDate, which is when the SUBSCRIPTION was created and says
     nothing about when its keys were last regenerated. Legacy tenant access exposes only an
     enabled flag. Activity Log is genuinely the only timestamp available.
  8. keyVault.lastStatus.timeStampUtc is a refresh timestamp, not a rotation timestamp. It
     records the last time APIM read the vault, which for an unversioned reference happens
     routinely. A recent value there proves nothing.
  9. Secrets written literally into policy XML. Policy GETs can return them, but there is no
     Reader-visible way to tell whether a literal was changed other than a policies/write event,
     which also fires for any unrelated policy edit.
  10. Adjacent credential stores whose inclusion in the flaw is not established by the primary
      source: self-hosted gateway tokens, developer portal delegation keys, and Credential
      manager (authorizations) connections. Enumerate them if the engagement allows, but this
      check does not rate them.
  11. Correlating Entra credentials to APIM objects depends on the APIM clientId matching an
      Entra appId. Where an OAuth server points at a non-Entra issuer, Step 4 returns nothing and
      that object falls back to Step 3 evidence only. The reverse also misleads: a secret rotated
      in Entra but never updated in APIM shows issuer-side rotation while the instance still
      carries the old one.
  12. Whether the Consumption tier is affected. The primary source names no tiers at all, and the
      tier scope used here comes from MZK9-GH0, which lists the four Classic tiers and excludes
      v2. Consumption sits in neither list. The Step 1 query flags it Consumption-UNRESOLVED
      rather than guessing. Resolve it against the client's own copy of the advisory.
  13. Reader scoped below subscription level makes Step 2 and Step 3 silently incomplete. Confirm
      the assignment scope before rating anything not_exposed, and record which subscriptions
      were actually readable.
false_positives: |
  States that match the exposed condition but are benign:
  - An instance whose named values are all unversioned Key Vault references and whose secrets
    were rotated in the vault. Correct remediation, zero APIM activity-log events, reads as
    unrotated. See blind_spots 5 and 6 — verify by hand before reporting.
  - Named values marked secret: true that hold non-sensitive strings. Teams set the flag
    defensively on hostnames, environment labels and feature switches. The flag means encrypted
    at rest, not confidential.
  - An instance holding only backends with client certificates referenced from Key Vault and no
    other credential class — the thumbprint and the reference are visible, the material is not,
    and the vault is the rotation point.
  - A Classic instance created in the window but never put into service: it holds default objects
    only and no real credential ever reached it. Check subscriptions count and whether any API is
    published before rating.
  - An instance decommissioned and left in place for a cutover. Still matches, holds live
    credentials, and is worth reporting anyway — but rate it with that context.

  The inverse matters more, and the result_logic above cannot catch it on its own —
  evidence that looks like rotation but is not:
  - An IaC re-apply. An ARM, Bicep or Terraform deployment run after the fix writes every child
    resource it manages and produces a clean sweep of namedValues/write, backends/write and
    authorizationServers/write events, while writing back the SAME credential strings from the
    same unchanged variable file. This is the single most likely way to misrate an instance
    not_exposed. Before clearing any instance on Step 3 evidence, ask whether the writes came
    from a pipeline run and whether the values in that pipeline's variable store were changed.
  - A bulk write from a backup restore, which reinstates pre-window values and logs as rotation.
related_baseline: CIS Microsoft Azure Foundations — Key Vault and secrets management sections;
  MCSB IM-8 (restrict the exposure of credentials and secrets), DP-7 / DP-8 (secure key and
  certificate management), PV-7 (remediate software vulnerabilities). No benchmark control covers
  incident-driven credential rotation directly; this is an event-scoped check, not a baseline
  deviation, and should be reported as such.
recommendation: |
  Treat every credential held in an affected Classic instance during 18–19 November 2026 as known
  to an attacker, and rotate it regardless of what the evidence in this check shows — the
  evidence is a proxy and the cost of a missed credential is higher than the cost of a rotation.
  Rotate in the order the vendor guidance sets out: create the replacement at the issuing system
  first, update API Management, test, and only then revoke the old secret. Updating API Management
  alone leaves the old credential live wherever it is honoured.
  Cover every class the instance holds: secret named values, backend header / query /
  authorization credentials and client certificates, Event Hubs and other logger connection
  strings, OAuth 2.0 and OpenID Connect client secrets, developer portal sign-in provider
  secrets, API subscription keys, legacy management API access keys, and any credential written
  literally into a policy document.
  Then reduce what a repeat of this would reach: move named values to Key Vault references with
  a managed identity rather than values stored in the instance, replace keys and connection
  strings with managed identity wherever the target supports it, and disable legacy tenant access
  if nothing depends on it.
  Export the Activity Log to a Log Analytics workspace now. The 90-day window closes around
  17 February 2027 and takes the rotation record with it.
  Review subscriptions, users, backends and policies for objects nobody recognises, and check the
  client's own Service Health history for MZK9-GH0 to confirm whether Microsoft notified them
  directly.
confidence: medium — the inventory half is solid: the Classic tier filter, the secret-bearing
  object enumeration and the Reader-readability of every call are confirmed against the vendor
  API reference, and Entra passwordCredentials.startDateTime gives real issuer-side rotation
  evidence for the subset of secrets Entra issued. The rotation half is weaker by construction:
  no APIM object carries a modification timestamp, so rotation is inferred from control-plane
  write events, which an IaC re-apply fakes and a Key Vault-side rotation never produces. Rated
  medium rather than high also because the incident facts that set the tier scope and the date
  boundaries come from an advisory this check could not read.
